# Аудит yt-dlp, обновлений и диагностики

Дата: 2026-09-23.
Область: установка yt-dlp и JS-компонентов, жизненный цикл обновления, YouTube-канарейка, диагностика и ошибки текущего инцидента.

## Краткий вывод

В краш-репорте непосредственной причиной остановки было отклонение меню Telegram из-за Markdown, а не падение yt-dlp. Это не отменяет двух независимых эксплуатационных проблем: в Docker-образе не установлен поддерживаемый JavaScript runtime, а автообновление пакета выполняется после импорта кода yt-dlp и поэтому не гарантирует, что текущий процесс начнет использовать новую версию.

Версия из репорта `2026.8.18.122307.dev0` отстает от опубликованной nightly `2026.09.16.232951`, доступной на дату аудита. Основной образ при этом воспроизводимо ставит старую закрепленную версию из `requirements.txt`. Включение `YTDLP_AUTO_UPDATE` временно меняет контейнер, но не исходный lock-файл или образ.

Предлагаемая для Nuvio модель: версия yt-dlp и runtime входят в неизменяемый Docker-образ; scheduled CI автоматически готовит проверяемое обновление версии; канарейка следит за настоящей загрузкой и сигнализирует о проблемах. Не обновлять пакет через pip внутри уже работающего процесса. Подготовка PR, публикация образа и обновление контейнера на сервере являются тремя разными шагами.

## Обнаруженные проблемы

### P0 - автообновление не перезапускает уже импортированный yt-dlp

`main.py` импортирует `utils.canary` до запуска `ensure_latest_yt_dlp`; `utils.canary` на уровне модуля импортирует `utils.youtube_utils`, а тот сразу импортирует `yt_dlp`. Затем `pip install --upgrade` меняет файлы на диске, но Python продолжает использовать уже загруженные модули. То же самое происходит при обновлении из канарейки в работающем процессе. Лог может показать новую версию из метаданных пакета, хотя загруженный код остался прежним. Кроме того, pip может изменить транзитивные зависимости, которыми уже пользуются другие обработчики.

Доказательство: [main.py](../../main.py#L43), [utils/canary.py](../../utils/canary.py#L50), [utils/youtube_utils.py](../../utils/youtube_utils.py#L10), [utils/ytdlp_runtime.py](../../utils/ytdlp_runtime.py#L86).

### P0 - образ не содержит JavaScript runtime для YouTube

Зависимость `yt-dlp[default]` ставит пакет `yt-dlp-ejs`, но Dockerfile не устанавливает Deno, Node или другой поддерживаемый runtime. Краш-репорт напрямую содержит предупреждение, что runtime не найден, а решение n challenge провалилось. В актуальной инструкции yt-dlp указаны Deno 2.3+ как рекомендуемый runtime и необходимость EJS-компонента.

Доказательство: [Dockerfile](../../Dockerfile#L1), [requirements.in](../../requirements.in#L3), приложенный краш-репорт. Требования runtime: [yt-dlp EJS setup](https://github.com/yt-dlp/yt-dlp/wiki/EJS).

### P0 - Telegram Markdown может сорвать меню до начала загрузки

В инциденте обработчик собрал меню и передал его в `edit_text(parse_mode="Markdown")`; Telegram вернул `Can't parse entities`. Общий `except Exception` классифицировал ошибку рендеринга как `YT-UNKNOWN` и показал ошибку вместо кнопок. Следовательно, пользователь не мог запустить скачивание. В рабочей копии уже заменено экранирование заголовка на helper Telegram; изменение еще не подтверждено проверками или отправкой реального меню.

Доказательство: [utils/telegram_utils.py](../../utils/telegram_utils.py#L1682) и общий обработчик ниже. Изменение экранирования сейчас находится в незакоммиченном состоянии.

### P1 - автоматическое обновление по умолчанию отключено, а его результат трудно трактовать

`YTDLP_AUTO_UPDATE=false` задан в шаблоне окружения и является настройкой по умолчанию. Если обновление выключено, `ensure_latest_yt_dlp()` возвращает `attempted=False` и одновременно `succeeded=True`; это может выглядеть как успешная проверка, хотя новая версия не проверялась. При включении каждый запуск вызывает pip, независимо от того, появилась ли новая версия. Код считает нулевой exit code pip успехом и не проверяет повторно функциональность YouTube.

Доказательство: [config.py](../../config.py#L161), [.env.example](../../.env.example#L68), [utils/ytdlp_runtime.py](../../utils/ytdlp_runtime.py#L76).

### P1 - смена канала не гарантирует переход на выбранный выпуск

Каналы описывают не закрепленную версию, а аргументы `pip install --upgrade`. При переключении с более новой nightly на более старую stable команда без явного номера версии может оставить установленную nightly и завершиться успешно. Канал `master` использует движущийся архив GitHub с `--force-reinstall`; результат нельзя воспроизвести по одному значению `YTDLP_RELEASE_CHANNEL`. Ни один из режимов не сверяет фактический выпуск с выбранной политикой после установки.

Доказательство: [utils/ytdlp_runtime.py](../../utils/ytdlp_runtime.py#L44) и проверка только exit code pip ниже.

### P1 - обновление внутри контейнера временное и не воспроизводится

Docker-образ берет закрепленную версию из lock-файла. Установка через pip меняет слой контейнера на время его жизни; пересоздание возвращает закрепленную версию. У проекта уже есть ручная процедура обновления пина, но версия повторяется также в тесте и документации. Нет единой команды, которая обновляет входной pin, пересчитывает хеши и приводит связанные проверки в согласованное состояние.

Доказательство: [requirements.in](../../requirements.in#L3), [Dockerfile](../../Dockerfile#L25), [youtube-download-runbook.md](../../docs/technical/youtube-download-runbook.md#L203).

### P1 - путь от PR до работающего сервера отсутствует в механизме обновления

CI на push проверяет код и образ, но не публикует новый образ. Release workflow публикует образ только по тегу `v*`. Даже успешный release сам по себе не обновляет контейнер на сервере: Compose использует локально доступный образ, пока оператор не выполнит pull и recreate. Поэтому scheduled PR из плана будет автоматическим предложением обновления, а не автообновлением работающего бота.

Доказательство: [.github/workflows/ci.yml](../../.github/workflows/ci.yml#L1), [.github/workflows/release.yml](../../.github/workflows/release.yml#L1), [compose.yaml](../../compose.yaml#L40) и ручной шаг на сервере в [youtube-download-runbook.md](../../docs/technical/youtube-download-runbook.md#L224).

### P1 - выпуск проверяет WebUI, но не готовность бота

У сервиса `web` есть `/health` и Compose healthcheck; у сервиса `bot` healthcheck отсутствует. CI и release smoke поднимают из образа только `python -m web` и проверяют ответ WebUI. Поэтому успешная публикация образа подтверждает запуск WebUI, но не запуск polling, наличие Deno или реальное скачивание ботом. Автоматическая доставка нового образа без отдельного сигнала готовности бота опиралась бы на неверный критерий успеха.

Доказательство: [compose.yaml](../../compose.yaml#L40), [compose.yaml](../../compose.yaml#L86), [.github/workflows/ci.yml](../../.github/workflows/ci.yml#L124), [.github/workflows/release.yml](../../.github/workflows/release.yml#L135).

### P1 - автоматический сигнал о проблеме выключен по умолчанию

Канарейка скачивает контрольный ролик производственным путем, минуя кэш; это полезная проверка, а не только проверка наличия метаданных. Однако `CANARY_ENABLED=false` по умолчанию, поэтому без отдельной настройки бот не обнаружит регрессию сам. При сбое канарейка делает принудительный pip update и повтор, но повтор исполняется тем же процессом с уже загруженным yt-dlp. Суточный лимит обновления хранится только в памяти и сбрасывается при рестарте.

Доказательство: [config.py](../../config.py#L169), [utils/canary.py](../../utils/canary.py#L245).

### P1 - канарейка может пропустить сбой или сама завершиться без уведомления

Канарейка выбирает формат с бюджетом 50 МБ и вызывает `download_video()`. Но если основная попытка падает, тот же загрузчик может перейти на другой формат без этого бюджета, а затем на CLI fallback. CLI fallback не получает `http_chunk_size=10 МБ`, который указан у API-загрузки. Августовский инцидент зависел именно от размера Range, поэтому успешный CLI fallback не доказывает, что основной API-путь здоров. При этом запасной формат без ограничения может резко увеличить трафик и размер файла проверки.

`get_available_formats()` и выбор формата стоят вне обработчиков ошибок в `run_youtube_canary_check()`. Если одна из них бросит исключение, `_check_in_thread()` перехватит только таймаут, а `youtube_canary_job()` завершится до уведомления администратора. При таймауте ожидание потока прекращается, но сам поток может продолжить работу; следующий pip update и повторная проверка могут совпасть с ним по времени.

Доказательство: [utils/canary.py](../../utils/canary.py#L123), [utils/youtube_utils.py](../../utils/youtube_utils.py#L400), [utils/youtube_utils.py](../../utils/youtube_utils.py#L296), [utils/ytdlp_common.py](../../utils/ytdlp_common.py#L19). Различие CLI и API уже отмечено в [youtube-download-runbook.md](../../docs/technical/youtube-download-runbook.md#L108).

### P1 - хвост краш-репорта смешивает разные сессии

Разбор метаданных вызывается без `session_id`, и весь его вывод записывается под общим ключом. Затем `output_tail(session_id)` добавляет этот общий хвост к хвосту конкретной сессии. При параллельных запросах в отчет попадают предупреждения о других видео и платформах. В приложенном отчете рядом с Shorts присутствуют TikTok, Instagram и YouTube `jNQXAC9IVRw`; последний адрес является видео для проверки cookies. По этому хвосту нельзя уверенно приписать каждое предупреждение проблемному Shorts.

Доказательство: [utils/youtube_utils.py](../../utils/youtube_utils.py#L72), [utils/ytdlp_common.py](../../utils/ytdlp_common.py#L149), [utils/download_report.py](../../utils/download_report.py#L60), [utils/cookie_health.py](../../utils/cookie_health.py#L51).

### P1 - зависший разбор метаданных может занять поток после таймаута пользователя

Для YouTube `process_url()` уже получил `session_id`, но вызывает `run_blocking(get_video_info, url)` без него. В `get_video_info()` сетевые опции тоже применяются без `session_id`, поэтому не ставится хук отмены. `asyncio.wait_for()` прекращает ожидание после `BLOCKING_TASK_TIMEOUT`, но не останавливает поток с yt-dlp. При серии зависших разборов можно исчерпать пул загрузок, даже если пользователи уже получили ошибки таймаута.

Доказательство: [utils/telegram_utils.py](../../utils/telegram_utils.py#L1673), [utils/telegram_utils.py](../../utils/telegram_utils.py#L361), [utils/youtube_utils.py](../../utils/youtube_utils.py#L72), [utils/ytdlp_common.py](../../utils/ytdlp_common.py#L149).

### P1 - два механизма EJS допускают неожиданный сетевой источник

`yt-dlp-ejs` уже закреплен в lock-файле, но API-опции и CLI fallback дополнительно разрешают `ejs:github`. Если локальный EJS отсутствует или перестал подходить версии yt-dlp, приложение может загрузить скрипты с GitHub во время обработки ссылки. Это меняет воспроизводимость, доступность и диагностику: результат зависит от доступа к GitHub и от удаленного выпуска. Удалять fallback следует после проверки, что в образе есть совместимые локальные скрипты.

Доказательство: [requirements.txt](../../requirements.txt#L1194), [utils/ytdlp_common.py](../../utils/ytdlp_common.py#L29), [utils/youtube_utils.py](../../utils/youtube_utils.py#L323). Значение `ejs:github`: [yt-dlp EJS setup](https://github.com/yt-dlp/yt-dlp/wiki/EJS).

### P1 - `/admin` и краш-репорт показывают не полное состояние обновления

Краш-репорт включает установленную версию и канал, но не показывает, включен ли updater, когда была последняя попытка, чем она завершилась, присутствует ли JS runtime и прошла ли канарейка после рестарта. Поэтому по одному отчету нельзя отличить актуальный пакет без runtime от неудачной установки или успешного обновления, которое еще не вступило в силу.

Доказательство: сборка полей отчета в [utils/telegram_utils.py](../../utils/telegram_utils.py#L281); runtime-версия логируется при старте в [main.py](../../main.py#L344).

### P1 - отказ доставки уведомления не виден администратору

Канарейка и краш-репорт ловят ошибку отправки администратору и пишут ее только на уровне DEBUG. Если Telegram недоступен или отправка запрещена, оператор может не получить сигнал о сбое YouTube, а штатный `LOG_LEVEL=INFO` не покажет причину недоставки. Нужны видимое состояние последней попытки уведомления и запись ошибки на рабочем уровне логирования; дополнительный канал оповещения можно выбирать отдельно.

Доказательство: [utils/canary.py](../../utils/canary.py#L304), [utils/telegram_utils.py](../../utils/telegram_utils.py#L321), [.env.example](../../.env.example#L39).

### P2 - обновление создает лишнюю задержку старта и меняет зависимости на лету

При включенной настройке каждый старт ожидает pip, с таймаутом до 240 секунд. Обновление из канарейки может происходить во время пользовательских загрузок. pip меняет код пакета на диске, пока приложение продолжает работу; результат обновления не изолирован и не становится активным согласованно.

Доказательство: [utils/ytdlp_runtime.py](../../utils/ytdlp_runtime.py#L94), [utils/canary.py](../../utils/canary.py#L247).

### P2 - текущие автоматические проверки не закрепляют контракт обновления

Найден тест сборки команд для каналов stable/nightly/master, но не обнаружены проверки полного поведения updater: отключенное состояние, ошибка pip, таймаут, отличие установленной версии до/после, перезапуск/применение обновления и наличие JS runtime в готовом образе.

Доказательство: единственное прямое покрытие builder находится в [test_audit_regressions.py](../../tests/test_audit_regressions.py#L1899); CI собирает Docker-образ, но в описанном job нет проверки, что в нем реально доступен runtime и решается JS challenge.

### P2 - диагностика cookies может усиливать массовый сбой

При каждой ошибке YouTube, TikTok или Instagram фоновый отчет вызывает `check_cookie_health()`. Результат кэшируется на 10 минут, но до появления записи параллельные ошибки могут запустить несколько одинаковых сетевых проб. Для YouTube проба обращается к отдельному ролику через yt-dlp и может занять до сетевых таймаутов, добавляя нагрузку как раз во время массовой поломки платформы. `probe_failed` в отчете относится к этой дополнительной проверке и не устанавливает причину пользовательского отказа.

Доказательство: [utils/telegram_utils.py](../../utils/telegram_utils.py#L1062), [utils/cookie_health.py](../../utils/cookie_health.py#L22), [utils/cookie_health.py](../../utils/cookie_health.py#L274).

### P2 - runbook противоречит текущей маршрутизации `MEDIA_FORBIDDEN`

Runbook дважды говорит, что при `MEDIA_FORBIDDEN` админам не отправляется краш-репорт. Код `_should_notify_admins_platform_failure()` возвращает `True` для этой категории, если этап не является timeout. Это создает неверные ожидания при расследовании массового 403. Перед исправлением документации нужно проверить реальный формат сообщения и договориться о нужной частоте оповещений.

Доказательство: [youtube-download-runbook.md](../../docs/technical/youtube-download-runbook.md#L80), [utils/telegram_utils.py](../../utils/telegram_utils.py#L1035).

## План исправлений

### Этап 0 - зафиксировать исходное состояние

1. Записать без секретов фактические настройки production: digest и тег запущенного образа, версию yt-dlp из пакета и загруженного модуля, Deno/EJS, `YTDLP_AUTO_UPDATE`, `CANARY_ENABLED`, время последней успешной загрузки.
2. Зафиксировать минимум измерений до правок: долю успешных загрузок YouTube, задержку от ссылки до меню и до первого байта, длительность полного скачивания, число ошибок по категориям, занятость пула загрузок, время/трафик канарейки. Если готовых метрик нет, собрать короткий воспроизводимый замер и не выдавать его за долгосрочную статистику.
3. Воспроизвести исходный сбой меню на проблемном Shorts и отдельно проверить длинный контрольный ролик без кэша. Сохранить текущий digest образа как точку отката.

**Готово, когда:** известны работающая версия, конфигурация и исходные результаты двух пользовательских сценариев; выбран образ для возврата при неудачном обновлении.

### Этап 1 - остановить текущие отказы меню и YouTube

1. Подтвердить экранирование заголовков Telegram Markdown специальными символами, Unicode, обратными слешами и пустыми полями. Если Telegram все же отклонит разметку, повторить показ меню обычным текстом с той же клавиатурой. Классифицировать отказ Telegram отдельно от ошибки YouTube. ### Этап 2 - сделать обновление простым и воспроизводимым

1. Убрать обновление pip из работающего процесса. Считать Docker-образ неизменяемой единицей релиза.
2. Добавить одну команду обновления yt-dlp, которая меняет pin в `requirements.in`, пересобирает lock-файл с хешами, обновляет все необходимые ссылки на версию, запускает проверки и показывает diff. Скрипт должен задавать конкретную версию; смена канала без версии не является откатом.
3. Добавить scheduled workflow, который периодически предлагает обновление до свежей nightly (или stable по выбранной политике) отдельным PR. PR должен пройти CI, сборку образа и YouTube smoke до слияния. Это автоматическая подготовка, а не установка на сервер.

5. Упростить каналы до реально поддерживаемых продуктом режимов; `master` требует отдельной политики риска и воспроизводимости, так как URL исходного архива не закрепляет неизменяемый артефакт.

**Готово, когда:** обновление можно открыть одной командой или scheduled PR; чистая сборка ставит ровно ту версию, что показана в отчете; откат выполняется возвратом к прежнему pin/образу.
